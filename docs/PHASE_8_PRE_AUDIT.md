## 1. Executive Summary

   (`hm-data.js:255–266`) מטביעה `cid` על כל תלמיד ב-`stu.list`, ועוד

   מחזיק רק `cls`» — **אינה מדויקת**.
2. **הפער האמיתי אינו כתיבה אלא קריאה.** `[הסקה]` `cid` נכתב על
   מדידות, על תלמידים ועל שיעורים — ו**כמעט אף מסלול קריאה לא משתמש
   בו**. כל שאילתות המדידה מצמצמות לפי `clsKey(r.cls)`, כלומר לפי שם.
3. **‎8‎ השוואות גולמיות** (`s.cls===X`) על זהות תלמיד־כיתה: ‎4‎
   ב-`hm-new.js`, ‎4‎ ב-`hm-tools.js`. `[עובדה]` המספר בדוח הקודם היה
   נכון.
4. **‎13‎ השוואות מנורמלות נוספות** (`clsKey(...)===`) שהן זהות לכל דבר,
   רק סלחנית יותר: ‎5‎ ב-`hm-data.js`, ‎7‎ ב-`hm-tests.js`, ‎1‎ עוזר
   ב-`hm-tools.js` (‎5‎ אתרי קריאה). **סה״כ ‎21‎ אתרי זהות-לפי-שם.**
5. **‎4‎ השוואות `cid` בלבד בכל האפליקציה** `[עובדה]` — שתיים בשכבת
   השיעור (`hm-data.js:991,1038`) ושתיים בפתיחת שיעור
   (`hm-tests.js:346,2084`). ‎2‎ «התאמות» נוספות הן `t.cat===cid` —
   **מזהה קטגוריית מבחן**, לא כיתה.

7. **שלושה מסלולי יצירת תלמיד אינם כותבים `cid`** `[עובדה]`

`[הסקה]` **הם ניתנים לאיחוד רק עם מיגרציה, ורק אם מוותרים על צורת

## 13. Backward Compatibility

### 13.1 שתי הצורות

```js
/* ישן  — לפני המיגרציה או משלושת מסלולי היצירה */   { id, name, cls:"ט׳3" }
/* חדש  — אחרי המיגרציה או מעריכה/ייבוא CSV      */   { id, name, cls:"ט׳3", cid:"c:ט:3" }
```

| שאלה | תשובה |
|---|---|
| **יכולות לדור בכפיפה אחת?** | **✅ כן, והן כבר עושות את זה היום.** `[עובדה]` `mig_classIdentity` מוסיף `cid` **לצד** `cls` ולא במקומו |
| **איפה מתבצע הנירמול?** | `classId(raw)` — `hm-data.js:67`. נקודה אחת, טהורה, מכוסה |
| **האם כדאי לשמור את `cls` זמנית?** | **✅ כן — ולא זמנית.** ראו למטה |
| **איפה זהות כפולה יוצרת עמימות?** | ראו §13.2 |
| **יש חלון תאימות בטוח?** | **✅ כן, והוא לא צריך להיסגר** |

### 13.2 שלוש נקודות עמימות אמיתיות

**א. `cid` שנגזר מתווית מול `cid` מהרישום.** `[עובדה]` `hm-new.js:132`
קורא `classId(s.cls)` ישירות — **לא** `findClass()`. אחרי שינוי שם,
עריכת כרטיס תלמיד תייצר `cid` **שונה** מזה שברישום. זו העמימות המסוכנת
ביותר שמצאתי.

**ב. `cls` ריק.** `hm-new.js:170` יוצר `cls:""` → `classId("")` מחזיר
`null`. תלמיד בלי כיתה הוא מצב חוקי, ולכן `cid:null` חייב להיות מצב
מותר ולא שגיאה.

**ג. `cls` ו-`cid` שסותרים.** אם מסלול אחד יעדכן `cls` ולא `cid` —
מי מנצח? `[המלצה]` כלל אחד, כתוב: **`cid` הוא הזהות; `cls` הוא ההקשר.
כשהם סותרים — `cid` קובע, ו-`cls` מתוקן ממנו.**

`[המלצה]` **אל תמחקו את `cls` מהתלמיד. אף פעם.** הוא ההקשר ההיסטורי,
בדיוק כמו `clsSnapshot` בשיעור ו-`name` על מדידה. שלב ‎5‎ כבר קבע את
הכלל הזה ושלב ‎8‎ צריך לרשת אותו, לא להמציא אחר.

## 15. Proposed PHASE 8 Architecture

> `[המלצה]` — כל הפרק הזה דעה. הוא נגזר מהעובדות שלמעלה, ולא מהמשימה.

### 15.1 מה **לא** להמליץ, ולמה

המשימה הציעה:

```
Student { sid, cid, name, … }        ← להוסיף cid
Class   { cid, name, … }             ← כבר קיים
```

`[הסקה]` **החצי הראשון כבר קיים** (§3.2, §11.1), והחצי השני קיים
במלואו. לכן ההצעה כלשונה **מתארת בעיקר את ההווה**, ואם ניישם רק אותה
נסיים שלב שלם בלי לשנות התנהגות אחת.

**וגם:** איחוד `stu.list` עם `ft.roster` — הפיתוי הגדול — הוא
**המלצה שלילית**. שלוש סיבות:

1. **צורות שונות מהותית.** `ft.roster` הוא מפה `{כיתה: [תלמידים]}`,
   `stu.list` הוא מערך שטוח. איחוד מחייב מיגרציה של שתי המבנים ונגיעה
   ב-`hm-tests.js` בכל אתרי ה-`roster()`.
2. **סמנטיקה שונה.** ‎`ft.roster`‎ הוא «מי בכיתה הזאת **עכשיו**»;
   `stu.list` הוא «תיק התלמיד **לאורך זמן**». תלמיד שעזב את בית הספר
   יורד מה-roster ונשאר בתיק.
3. **‎21‎ אתרי קריאה ב-`hm-tests.js`** יידרשו שינוי בו-זמנית. זו
   הגדרה של refactor רחב, ושל «כתיבה מחדש» — בדיוק מה שהפרויקט אוסר.

### 15.2 ההמלצה: **הפוך את `cid` לקריא, אל תשנה את הצורה**

```
שכבה 0 — עוזר אחד, טהור, ב-hm-data.js
  cidOfStudent(stud, store) → "c:ט:3" | "cn:…" | null
     1. stud.cid אם קיים ותקף            ← הזהות
     2. findClass(store, stud.cls).id    ← דרך הרישום (עומד בשינוי שם)
     3. classId(stud.cls)                ← נפילה אחורה, כמו היום
     4. null                             ← תלמיד בלי כיתה — מצב חוקי

שכבה 1 — השלמה, לא המרה
  שלושת מסלולי היצירה (hm-new.js:170,620,814) כותבים cid
  מיגרציה 3→4 משלימה cid לכל מי שחסר

שכבה 2 — הקריאה עוברת ל-cid
  8 ההשוואות הגולמיות (§6.1)  →  cidOfStudent(s)===cidF
  ft.roster נשאר כפי שהוא, מפתוח לפי clsKey
  measurementsOf מקבל opts.cid לצד opts.cls — תוספת, לא החלפה
```

**ארבעה כללים שמגבילים את ההמלצה:**

1. **`cls` לא נמחק לעולם.** הקשר היסטורי, כמו `clsSnapshot` ו-`name`.
2. **`ft.roster` לא משנה צורה בשלב ‎8‎.** המפתוח לפי `clsKey` נשאר.
3. **`tools.att` לא משנה צורה.** ההחלטה משלב ‎7‎ עומדת.
4. **אף מסלול לא נחסם בגלל `cid` חסר.** `cidOfStudent` מחזיר `null`
   ואז ההתנהגות **זהה להיום**. זה מה שמנטרל את סיכון **A2**.

`[הסקה]` **יתרון מכריע:** כל שלב מהשלושה ניתן לשילוח בנפרד, וכל אחד
מהם בטוח לבדו. שכבה ‎0‎ לבדה אינה משנה התנהגות כלל.
