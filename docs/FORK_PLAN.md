## 1. בשורה אחת

שכפול הקוד הוא החלק הקל — פקודה אחת.
**הקושי האמיתי הוא שהמגרש PRO והשכפול חולקים דברים שאינם בקוד:** מרחב
האחסון בדפדפן, מטמון האופליין, תיקיית הגיבוי בדרייב, גיליון השיאים
המשותף, והאייקון במסך הבית. אם לא מנתקים אותם אחד-אחד, השכפול **יפגע**
במגרש PRO — לא בגלל באג, אלא בגלל שהוא מצליח.

התגלית החמורה ביותר במסמך הזה:

> ה-service worker מוחק בכל הפעלה כל מטמון שמתחיל ב-`hamegrash-` ואינו
> שלו. שתי אפליקציות באותו origin עם אותה תחילית **מוחקות זו לזו את
> מטמון האופליין בכל פתיחה.** המגרש PRO מפסיק לעבוד בלי רשת — במגרש,
> בלי שאיש יבין למה.

ההמלצה: **ריפו חדש ועצמאי עם היסטוריה מלאה (לא Fork של GitHub), מתארח
על origin אחר לגמרי, ובכל זאת מחליף את כל מזהי הזהות הפנימיים.** חגורה
וגם שלייקס — כי המורה עלול לפתוח את שתיהן גם מקובץ מקומי, ושם כללי
ה-origin מתנהגים אחרת בכל דפדפן.

## 3. ההתנגשויות — החלק הקריטי

מיפוי מלא ממה שקיים בקוד היום:

### 3.1 מטמון האופליין — מחיקה הדדית

בקובץ `sw.js`:

```js
const CACHE = "hamegrash-" + CACHE_VERSION;
// ב-activate:
keys.filter(k => k.startsWith("hamegrash-") && k !== CACHE && !k.endsWith("-fonts"))
    .map(k => caches.delete(k))
```

הלוגיקה הזאת נכונה לחלוטין לאפליקציה אחת — היא מונעת מטמון ישן שנתקע.
ברגע שיש שתיים באותו origin היא הופכת לנשק. כל פתיחה של אחת מוחקת את
השנייה.

**פתרון:** בשכפול, תחילית מטמון אחרת לגמרי. לא `hamegrash-2`, אלא שם
שאין לו שום קידומת משותפת.

### 3.2 אחסון הנתונים

| מה | היכן בקוד | הערך היום |
|---|---|---|
| תחילית localStorage | `hm-app.js` שורות ‎42‎, ‎47‎, ‎4899‎ | `pehub.` |
| תחילית הגיבוי | `hm-app.js` שורה ‎1423‎ | `pehub.` |
| תפקיד המשתמש | `hm-app.js` שורות ‎148‎, ‎153‎, ‎169‎ (sessionStorage) | `pehub.role` |
| מסד סרטוני השיאים | `hm-app.js` שורות ‎1454‎, ‎3817‎, ‎4527‎ | `pehub-records` |

שתי אפליקציות שכותבות ל-`pehub.students` — האחרונה שנשמרה מנצחת. מורה
שמנסה את השכפול ומאבד את רשימות הכיתות במגרש PRO לא יחזור לשתיהן.

ההתחלה קלה: התחילית מופיעה במעט מאוד מקומות בקוד — אבל היא מופיעה גם
בבדיקות: ‎17‎ אזכורים בבדיקות היחידה ועוד כ-‎13‎ בבדיקות הדפדפן. שינוי
בלי עדכון הבדיקות = CI אדום.

### 3.3 הגיבוי לגוגל דרייב

```
GDRIVE_FOLDER_NAME = "המגרש PRO – גיבויים"
```

שתי האפליקציות יוצרות/מוצאות אותה תיקייה בדרייב ומעלות אליה קבצים
באותה תבנית שם. בנוסף, `bk.gdFolderId` נשמר ב-localStorage — כלומר
בהתנגשות של סעיף ‎3.2‎ השכפול "יורש" את מזהה התיקייה של המגרש PRO.

**עוד נקודה שקל לפספס:** ה-Client ID של גוגל שהמורה יוצר בעצמו כולל
רשימת *Authorized JavaScript origins*. אם השכפול יושב על origin אחר —
והוא צריך לשבת על origin אחר — המורה חייב להוסיף אותו שם, אחרת הגיבוי
לדרייב פשוט לא יתחבר. זה לא באג, זו הגדרה, וצריך שהיא תופיע ב-README
של השכפול.

### 3.4 קובץ הגיבוי עצמו

```js
var BK_APP = "hamegrash-pro";
var BK_V   = 2;
var SCHEMA_VERSION = 4;
```

הייבוא בודק `v` ו-`schema` אבל **אינו בודק את `app` בכלל.** כלומר קובץ
גיבוי מהשכפול ייובא בשקט לתוך המגרש PRO. כל עוד הסכמה זהה זה אפילו
נוח — אפשר להעביר נתונים בין השניים. ברגע שהשכפול יעלה סכמה ל-‎5‎,
המגרש PRO יזרוק `newer-schema` וזה בסדר; אבל אם השכפול יוסיף שדות
*באותה* גרסת סכמה, הייבוא יצליח ויכניס נתונים שהמגרש PRO לא מבין.

**החלטה נדרשת:** האם תאימות גיבוי דו-כיוונית היא תכונה שרוצים לשמור?
- אם כן — לשמור `BK_APP` זהה, ולסמן במסמך שהסכמה משותפת ומקודמת יחד.
- אם לא — להחליף `BK_APP` בשכפול, ולהוסיף בדיקת `app` בייבוא (שינוי
  קטן, אבל הוא נוגע במגרש PRO — ראו שלב ‎1‎).

### 3.5 שרת סנכרון השיאים

`sync-backend/Code.gs` הוא Apps Script שמחובר לגיליון, עם `SYNC_CODE`
בית-ספרי. אם השכפול יופנה לאותו deployment — שתי האפליקציות כותבות
לאותה טבלת `records`, עם לוגיקת מיזוג שנכתבה לאפליקציה אחת.

**פתרון:** deployment וגיליון נפרדים לשכפול. עלות: אפס. סיכון בהתעלמות:
טבלת שיאים מזוהמת אצל בית ספר אמיתי.

### 3.6 זהות ה-PWA

`manifest.webmanifest` — אותו `name`, אותו `short_name`, אותם שלושה
אייקונים, אותו `theme_color`. מורה שמתקין את שתיהן מקבל שני אייקונים
זהים במסך הבית ואין לו דרך להבדיל ביניהם. זה גם פוגע במגרש PRO: תלונה
של "האפליקציה מחקה לי הכול" תגיע על המוצר הלא נכון.

### 3.7 קישורים קשיחים

```
https://osher15.github.io/Pro-sport-pa/tochnit-shnatit/tochnit-shnatit.ics
```

שלושה קישורי ICS ב-`tochnit-shnatit/ap-app.js` מצביעים לאתר של המגרש
PRO. בשכפול הם יציגו למורה כתובת של מוצר אחר. ראו סעיף ‎8‎ — כנראה
עדיף שהתת-אפליקציה הזאת בכלל לא תיכנס לשכפול.

## 5. אפשרות ב׳ — איפה הוא מתארח

זו ההחלטה שקובעת אם התנגשויות סעיף ‎3‎ הן בעיה חמורה או בעיה תיאורטית.

| | ב1 · Pages באותו חשבון | ב2 · Pages בחשבון/ארגון אחר | ב3 · Netlify / Cloudflare Pages | ב4 · דומיין משלו |
|---|---|---|---|---|
| כתובת | `osher15.github.io/<שם>/` | `<חשבון>.github.io/<שם>/` | `<שם>.netlify.app` | `app.example.com` |
| origin נפרד | ❌ **לא** | ✅ | ✅ | ✅ |
| עלות | 0 | 0 | 0 | ~‎50‎ ₪ לשנה |
| מאמץ הקמה | אפס | נמוך | נמוך | בינוני |
| מראה מקצועי | בינוני | בינוני | בינוני | גבוה |
| התנגשות אחסון | **כל סעיף ‎3.2‎–‎3.1‎ בתוקף** | נמנעת | נמנעת | נמנעת |

**המלצה: ב3 בטווח הקצר, ב4 כשהמוצר מתבשל.**
Netlify או Cloudflare Pages נותנים origin נפרד לגמרי בחינם, בלי לגעת
בהגדרות ה-Pages של המגרש PRO ובלי לפתוח חשבון GitHub נוסף. הפריסה
מחוברת ל-main של הריפו החדש בדיוק כמו היום.

**ב1 היא המלכודת.** היא הכי קלה, היא נראית נפרדת לגמרי — ריפו אחר,
תיקייה אחרת, service worker אחר — ובכל זאת שתי האפליקציות חולקות את
אותה קופסת אחסון. זו בדיוק הדרך שבה השכפול "יעלה על" המגרש PRO.

**גם עם origin נפרד — עדיין מחליפים את המזהים הפנימיים.** שתי סיבות:
המגרש PRO נועד לרוץ גם מקובץ יחיד מקומי, ושם התנהגות ה-origin משתנה
בין דפדפנים; ובעתיד, אם אי פעם שניהם ישבו תחת אותו דומיין, הבעיה תחזור
כשכבר יהיו נתונים אמיתיים בפנים.

## 6. אפשרות ג׳ — איך מעבירים תיקונים בין השניים

השאלה שתכריע כמה כואב לתחזק שני מוצרים. באג שמתגלה במגרש PRO — למשל
בחישוב VO₂max או במיגרציית סכמה — קיים גם בשכפול.

| | ג1 · ניתוק מלא | ג2 · ריפו נפרד + cherry-pick | ג3 · ליבה משותפת |
|---|---|---|---|
| איך | כל תיקון נכתב פעמיים | `git remote add pro …` ואז cherry-pick | `hm-data.js` כחבילה/תת-מודול משותף |
| מאמץ הקמה | אפס | דקות | ימים |
| מאמץ שוטף | **כפול לנצח** | נמוך, כל עוד הנתיבים זהים | נמוך מאוד |
| חופש לשנות ארכיטקטורה | מלא | מלא | **מוגבל — הליבה כבולה** |
| סיכון לשבור את PRO | אפס | אפס (הזרימה חד-כיוונית) | **קיים — שינוי בליבה נוגע בשניהם** |

**המלצה: ג2.** היא היחידה שנותנת גם עצמאות מלאה וגם דרך חזרה.
התנאי היחיד שלה: **לא לשנות שמות קבצים ולא לשנות מבנה תיקיות בשכפול.**
ברגע ש-`hm-app.js` הופך ל-`xx-app.js`, כל cherry-pick הופך לעריכה ידנית.

ג3 (ליבה משותפת) נשמעת הכי "נכונה הנדסית" והיא הכי מסוכנת כאן: היא
בדיוק מה שביקשת שלא יקרה — שינוי בשכפול שנוגע במגרש PRO. אפשר לחזור
אליה בעתיד אם יתברר שהליבה באמת יציבה, לא לפני.

## 7. תפר הזהות — הרעיון שמייעל את כל השאר

יש מתח בין שתי הדרישות:

- סעיף ‎3‎ דורש להחליף את כל מזהי הזהות בשכפול.
- סעיף ‎6‎ דורש שהקבצים יישארו זהים ככל האפשר, אחרת cherry-pick נשבר.

המזהים האלה פזורים היום על פני חמישה קבצים. כל תיקון עתידי שייגע
בקובץ כזה ייצור קונפליקט — לנצח.

**הפתרון: לרכז את כל מזהי הזהות בקובץ אחד**, למשל `hm-brand.js`:

```js
/* כל מה שמבדיל בין מוצר למוצר — ורק זה. */
var BRAND = {
  ns:        "pehub.",              /* תחילית localStorage/sessionStorage */
  idb:       "pehub-records",       /* מסד סרטוני השיאים */
  cache:     "hamegrash-",          /* תחילית Cache Storage */
  backupApp: "hamegrash-pro",       /* שדה app בקובץ הגיבוי */
  driveDir:  "המגרש PRO – גיבויים", /* תיקיית הגיבוי בדרייב */
  fileName:  "Hamegrash.html"       /* שם הקובץ היחיד */
};
```

התוצאה: שני הריפוז מחזיקים קוד **זהה בית-בית**, חוץ מקובץ אחד קצר.
cherry-pick של תיקון מהמגרש PRO לשכפול עובר בלי קונפליקט כמעט תמיד.

### מה זה דורש מהמגרש PRO

זהו השינוי היחיד שהמסמך הזה מציע לעשות במגרש PRO עצמו — ולכן צריך
להיות ברור לגביו:

- **הערכים נשארים זהים לחלוטין.** `pehub.` נשאר `pehub.`. אין מיגרציה,
  אין שינוי התנהגות, אין נגיעה בנתוני מורה קיים.
- זהו refactor מכני: להוציא קבועים למקום אחד ולהפנות אליו.

- [ ] גיבוי לדרייב מכל אחת — **שתי תיקיות שונות** בדרייב
- [ ] שתי האפליקציות במסך הבית — שם ואייקון שונים, ניתנות להבחנה

## 12. מה השכפול אמור לעשות שהמגרש PRO לא יכול

זו הסיבה היחידה שמצדיקה את כל הכאב שלמעלה. `VISION.md` כבר מזהה את
החולשות שיעצרו צמיחה, וכולן ארכיטקטוניות — כלומר בדיוק הדברים שמסוכן
לעשות במוצר שמורים משתמשים בו בשדה היום:

| מה שחסום היום במגרש PRO | למה הוא חסום | בשכפול |
|---|---|---|
| פיצול `hm-app.js` (‎3,475‎ שורות) | שינוי רוחבי בקובץ שנוגע בכל מסך | חופשי — אין משתמשים לשבור |
| TypeScript | מחייב שלב build שיפגע ב"אין build לפיתוח" | אפשר לבחון עד הסוף |
| מודל "בית ספר" / כמה מורים | משנה את מודל הנתונים מהיסוד | **זה הצעד הגדול האמיתי** |
| נורמות בינלאומיות | הסכמה מניחה פורמט ישראלי | סכמה חדשה מאפס |
| ניתוק `support.js` מ-unpkg | נקודת כשל חיצונית שקשה להזיז בזהירות | לנקות בהתחלה |
| ציונים מעבר לפורמט הישראלי | קשור לתעודה אחת | מודל הערכה כללי |

**הסדר שמומלץ בשכפול, אחרי שהבידוד עובד:**
‎1‎. לנקות תלויות חיצוניות · ‎2‎. לפצל את הליבה למודולים · ‎3‎. **מודל
בית ספר / כמה מורים** — זה השינוי שהמגרש PRO לעולם לא יוכל לעשות
בבטחה · ‎4‎. i18n אמיתי ונורמות בינלאומיות.

הליבה של אפשרות זו: המגרש PRO ממשיך לקבל תיקוני באגים ולהיות יציב.
השכפול לוקח את הסיכונים. ואם השכפול מצליח — יש מוצר שני; ואם לא —
לא קרה כלום למגרש PRO. זו כל מטרת ההפרדה.
