## 2. Core Product — היום מול מחר

### השרשרת שנשאלה עליה

```
Teacher → Class → Student → Lesson → Measurement → Assessment → Progress → Report
```

| חוליה | מצב | ראיה |
| --- | --- | --- |
| **Teacher** | ❌ לא קיימת | אין ישות. מכשיר = מורה |
| **Class** | 🟡 מרומזת | מפתח מחרוזת `clsKey`, לא ישות |
| **Student** | ⚠️ **כפולה** | `stu.list` **וגם** `ft.roster` — שתי רשימות |
| **Lesson** | ✅ קיימת, **מנותקת** | `ls.lib` — אין קשר לתלמיד או למדידה |
| **Measurement** | ✅ חזקה | `ft.results` — ריבוי ניסיונות, תאריכים |
| **Assessment** | ✅ חזקה | ניקוד, נורמות, מדד |
| **Progress** | 🟡 חלקית | שיפור מחושב **תוך מבחן**, לא לאורך זמן חוצה מבחנים |
| **Report** | ✅ קיימת | דוח תלמיד + כיתה |

### 1. מה קיים
Measurement · Assessment · Report — **שלוש החוליות החזקות**.

### 2. מה קיים אבל מנותק
- **Lesson** — מערך נשמר ונטען, אך **לא יודע מי השתתף ומה נמדד בו**
- **שיאים** — היסטוריה נפרדת לגמרי מ-`ft.results`
- **ביפ טסט** — `bt.results` הוא **סכמה שונה**; החיבור למבחנים הוא **ייצוא ידני** (`bt-toFt`)
- **`tochnit-shnatit/`** — מנותקת לחלוטין

### 3. מה חסר
- **מזהה תלמיד יציב** — 🔴 החסם המרכזי
- **Teacher / School** — לא קיימות
- **Progress חוצה־מבחנים** — אין ציר זמן אחד לתלמיד
- **מעבר בין כיתות / שנים** — אין מודל שנת לימודים

### 4. Duplication
| כפילות | מיקום |
| --- | --- |
| שתי רשימות תלמידים | `stu.list` ↔ `ft.roster` |
| שתי סכמות תוצאה | `ft.results` ↔ `bt.results` |
| שתי ספריות תרגילים | `hm-build.js` (‎101‎) ↔ `FIT._test.EX` (‎47‎) |
| שני בוררי כיתה | `FT.pick` ↔ `#stu-classSel` |

**לא כפול (לטובה):** לוגיקת הניקוד מרוכזת ב-`hm-tests.js` בלבד — ‎10‎ מופעים שם, **‎0‎** בשאר הקבצים.

### 5. Workflows שלא מחוברים
- מערך שיעור → אין «התחל שיעור» שפותח מדידה
- ביפ טסט → דורש לחיצה ידנית כדי להגיע למעקב
- שיאים → אינם מזינים את מדד הכושר
- תזונה, ידע, כלי כיתה → **איים גמורים**

### Core היום
> **מדידה מהירה בשיעור + ניקוד מול נורמה.**

### Core שצריך להיות
> **פרופיל כושר של תלמיד לאורך שנים, שכל כלי מדידה מזין אותו.**

ההבדל אינו פיצ׳ר — הוא **תיקון מודל הנתונים**.

## 5. Photo Finish — הערכה כנה

### מה באמת קיים (`hm-app.js:1086–2007`)

| רכיב | מימוש |
| --- | --- |
| גישה למצלמה | `getUserMedia`, בחירת מצלמה, זום, היפוך |
| עיבוד | `getImageData` על פס `BANDW`, לומיננסיה לפי תא |
| זיהוי | רקע אדפטיבי (`bg[c] += (lum-bg[c])*α`), סף יחסי |
| חימום | ‎30‎ פריימים לפני חימוש |
| רצועה | `captureStrip` בכל פריים ← ציר אופקי = זמן |
| תיקון ידני | לחיצה על הרץ ← אינטרפולציה בין עמודות |
| קיזוז אקדח | מרחק ÷ ‎343‎ מ/ש |

### 🔴 מגבלות שחייבות להיאמר

1. **הדגימה מוגבלת ל-`requestAnimationFrame`** — כלומר **‎~60Hz‎ = רזולוציה של ‎~16.7‎ מ״ש**, לא מילישניות. **הדיוק ה«מילישנייתי» מגיע מהאינטרפולציה הידנית, לא מהטריגר האוטומטי.**
2. **חלון עיוור של ‎450‎ מ״ש** (`hm-app.js:1189`) — שני רצים בהפרש קטן מזה **יירשמו כאחד**. זה **בדיוק** התרחיש של גמר צמוד.
3. **הזיהוי מבוסס לומיננסיה בלבד** — רץ בחולצה בגוון הרקע לא ייתפס. אין זיהוי צורה.
4. **תלוי ביציבות המצלמה** — הרקע האדפטיבי מתאפס בכל תזוזה.
5. **UNKNOWN: תאימות מכשירים.** לא נמדד על חומרה אמיתית. `getImageData` בכל פריים הוא הנתיב הכבד.

### האם זה Killer Feature?

**כן — אבל רק במסגור הנכון.**

- ❌ **לא** «תזמון מקצועי». הקוד אינו מצדיק את הטענה.
- ✅ **כן** «תמונת סיום שמאפשרת למורה **להכריע** מי ראשון, ולקרוא זמן בדיוק של עשיריות — מציוד שכבר יש לו».

**לזכות המוצר:** הוא **כבר עושה את המסגור הנכון** — מציג את רזולוציית הזמן שהושגה בפועל, מפעיל בדיקת שפיות, ומסייג במפורש. **זו יושרה הנדסית אמיתית.**
